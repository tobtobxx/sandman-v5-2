Android companion app for Sandman: stack options

On-device speech-to-text and text-to-speech, usable as the phone's assistant. Compared as of September 2026.

Recommendation, short

  • App: native Kotlin + Jetpack Compose. The assistant role, microphone foreground services and RecognitionService are Android-only APIs; every cross-platform option ends up writing them in Kotlin anyway.
  • Speech: sherpa-onnx as the engine layer (Silero VAD, a streaming Zipformer or Parakeet/Moonshine for STT, Piper or Kokoro for TTS). Put Android's own on-device SpeechRecognizer and TextToSpeech behind the same interface as the zero-download fallback.
  • Assistant entry: start with an ACTION_ASSIST activity (qualifies for the assistant role, ~1 day of work), move to a VoiceInteractionService with an overlay session later. Skip always-on wake word in v1.
  • Server link: Tailscale (or any WireGuard) to reach the host, the existing bearer api.token, POST /send with client_msg_id for offline-safe captures, SSE while open, UnifiedPush once Web Push (#43) exists server-side.

1. What the app has to do

From docs/DESIGN.md and docs/API.md, the phone app is a Sandman client with a voice layer:

  • Capture without choosing (G1): speak, get a transcript, POST /send {text, client_msg_id}. The design allows the client to transcribe on device and send text (§6.3), so no server STT is needed.
  • Speak back: capture.confirmed and briefing replies already carry a speech form (src/conversation/capture.ts, briefing.ts). The design puts TTS on the client in v5.
  • Answer the needs-you list by voice (G1b): briefings via POST /briefings and /briefings/:id/reply; questions are ≤25 words with 2–4 numbered options, so short-utterance STT is enough.
  • Driving use: hands-free, headset button, speech-only confirmations.
  • Notifications for push-level events when the app is closed.

Constraint that shapes everything: the server model is slow (seconds per desk turn). The app should acknowledge locally at once ("Got it") and speak the real confirmation when capture.confirmed arrives, instead of blocking the user.

Why native wins here. The hard parts of this app are not screens. They are: a bound VoiceInteractionService, a microphone foreground service that survives Android 14/15 restrictions, low-latency PCM streaming into a native inference library, audio focus and Bluetooth headset routing, and TTS ducking. All of that is Kotlin in every option. Flutter/RN add a bridge between the audio thread and the UI without removing any Kotlin. The screens themselves (home prompt, topic chat, needs-you list) are small.

Hybrid worth considering: native Kotlin app whose voice overlay, needs-you list and settings are Compose, and whose "open topic" screen is initially a WebView of the server's own client.html (token in the URL is already accepted, src/server.ts:256). That gets a full UI in week one and lets you replace screens one at a time.

3.3 Wake word and VAD

VAD

Silero VAD (bundled with sherpa-onnx, ~2 MB). Needed for end-of-speech detection and to stop Whisper-style models transcribing silence. Not optional.

Wake word

Options: sherpa-onnx keyword spotting (open vocabulary, define the phrase as text), openWakeWord (Apache-2.0, trainable), Porcupine (commercial, best battery). Third-party apps cannot use the DSP hotword path that preinstalled assistants use, so always-listening means a mic foreground service with a permanent notification and real battery cost.

Verdict

Leave wake word out of v1. Long-press power (assistant role), a Quick Settings tile, a widget and a headset button cover most of the "don't choose anything" use, including driving.

5. Talking to the Sandman host

Reachability

The server binds ::1:8700. Put the host and phone on Tailscale (or plain WireGuard) and bind the API to the tailnet address. Avoid exposing it publicly: there is one shared api.token until per-client tokens (#44) land.

Offline captures

Store each transcript in a local Room outbox with a client_msg_id and send with WorkManager. /send already dedupes by client_msg_id, so retries after network loss never file twice.

Live updates

OkHttp SSE on /events/stream?after= while the app or voice session is in the foreground. Don't hold SSE in the background; Android will kill it and it costs battery.

Push when closed

Options: FCM (needs Firebase and Google Play Services, server holds a Google key), UnifiedPush with a self-hosted ntfy (no Google), or polling. UnifiedPush 2.x speaks Web Push, so implementing Web Push (#43) once on the server serves both the browser client and the app. Recommended.

7. Suggested order of work

  1. Skeleton: settings (host, token), home prompt → /send, Room outbox, SSE, needs-you list. Topic screen as a WebView of client.html.
  2. Voice v0 with S1: platform on-device STT and TTS behind the engine interface; speak capture.confirmed.speech. This proves the loop and the latency budget before downloading any models.
  3. Assistant entry: ACTION_ASSIST activity, QS tile, share target.
  4. sherpa-onnx engines: model download manager, VAD, STT + TTS per language, hotwords from GET /topics titles.
  5. Briefing mode: voice loop over /briefings; "skip/repeat/stop" are already handled server-side.
  6. Push: after server Web Push (#43), add UnifiedPush.
  7. v2: VoiceInteractionService overlay, headset button, driving mode (needs client modes, #63), native topic screens.

8. Risks and open questions

  • Language. Which languages will you speak to it? English-only makes Moonshine + Kokoro attractive; German pushes toward Parakeet v3 or Whisper for STT and Piper for TTS. Mixed-language use favors Whisper/Parakeet v3.
  • Device class. Parakeet 0.6B and Kokoro want a recent phone (8 GB RAM, recent SoC). On a mid-range phone, Zipformer + Piper is the safe pair. Measure real-time factor on the actual device before choosing.
  • Android background rules. Microphone FGS cannot be started from the background on Android 14+; start voice sessions only from user-visible entry points (assistant gesture, tile, notification action).
  • Server gaps. Web Push (#43), per-client tokens (#44) and client modes (#63) are not implemented; the app works without them but push and driving mode depend on them.
  • On-device LLM. Gemini Nano via ML Kit Prompt API (beta) could handle offline intent parsing, but Sandman's harness does routing on the host; adding a second brain on the phone would duplicate that. Not recommended for now.
